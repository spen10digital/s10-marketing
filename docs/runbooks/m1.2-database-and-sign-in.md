# Runbook: M1.2 database and sign-in (dev)

Every AWS step here needs the owner's approval (CLAUDE.md, rule 5). Use PowerShell with a short-lived SSO session:

```powershell
aws sso login --profile s10-dev
$env:AWS_PROFILE = "s10-dev"
```

## 1. Review and deploy the stacks
```powershell
pnpm infra:diff
cd infra
npx cdk deploy S10Marketing-dev-Database S10Marketing-dev-Identity S10Marketing-dev-VercelAccess --exclusively --context env=dev --context alertEmail=<owner email>
cd ..
```
> Always pass `--context alertEmail=…` to CDK deploys and diffs. Without it, Core's diff shows the ops-alert email subscription being **removed**. `--exclusively` keeps CDK from also deploying stacks these depend on.
>
> Aurora drops old minor versions. If a deploy fails with `Cannot find version … for aurora-postgresql`, list the available versions with `aws rds describe-db-engine-versions --engine aurora-postgresql --region us-east-2` and bump `AuroraPostgresEngineVersion` in `database-stack.ts`.
- **Database:** Aurora Serverless v2 (0–4 ACU, pauses after 10 min), isolated VPC, `app_owner` and `app_rw` secrets, `db-*` parameters. Creating the cluster takes about 10 minutes.
- **Identity:** the `s10-identity-dev` user pool, managed login at `s10-identity-dev.auth.us-east-2.amazoncognito.com`, the `s10-marketing-web` client, and the `cognito-*` and `app-url` parameters.
- **VercelAccess:** the web role gains Data API access to this cluster and the `app_rw` secret only.

Recurring cost: two secrets (about $0.80/month), Aurora storage and backups (cents at this size), and compute only while the cluster is awake. Cognito Essentials is free up to 10k monthly active users.

## 2. Run the migrations
```powershell
pnpm db:migrate --aws --env dev
```
This applies `db/migrations/*` as `app_owner`, then sets `app_rw`'s login password from its secret. The first call may wait about 20 s while Aurora resumes.

## 3. Verify the Data API context assumption
```powershell
pnpm db:verify-context --env dev
```
Expected output: `role: app_rw`, `set_config visible … yes`, `leaked … no`, `OK`. If it fails, **stop**. Don't put the app in front of the database; fall back to explicit parameters to definer functions (02 §3.2).

## 4. Try the flow as a new user
1. Push `develop` (or redeploy it) so the `develop` branch alias picks up the new parameters.
2. Open `https://s10-marketing-git-develop-spen-10-digital.vercel.app` and choose **Create account**. Sign up, then enter the emailed code.
3. You land on **Welcome! Create your organization**. Create "S10" and then "LimitKeep" (switch between them in the sidebar).
4. Create brands and save a voice profile. Each save adds a version under **Voice history**.
5. Sign out, then sign back in.

Cognito's default email sender is limited to 50 emails a day. Moving it to SES comes with notifications (M2.4).

## Local development against dev Cognito
`http://localhost:3000` is a registered callback. Copy `COGNITO_USER_POOL_ID`, `COGNITO_CLIENT_ID` and `COGNITO_DOMAIN` from Parameter Store into `apps/web/.env.local`. These are public IDs, not secrets. Then:
```powershell
pnpm db:up
pnpm db:migrate
```
Set `DATABASE_URL=postgres://app_rw:<LOCAL_APP_RW_PASSWORD>@localhost:5432/s10_marketing` in `.env.local`, then run `pnpm dev`.

## Rotating a database password (manual)
1. Generate a new password value for the secret (`aws secretsmanager put-secret-value`, or use **Retrieve → Edit** in the console).
2. For `app_rw`, run `pnpm db:migrate --aws --env dev`; it re-applies the password.
3. For `app_owner`, use `aws rds modify-db-cluster --master-user-password` and update the secret to match.
